# 团队 RFC 规范与模板

> 本文定义本团队 RFC 的**整体要求**（结构、编号、语言、双受众、验收绑定、生命周期） 与**可复制骨架**（§9）。适用对象：系统设计、协议、训练方案、实验计划等一切 "先规格后实现"的工作。配套约定见 [AGENTS.md](../AGENTS.md) 的 RFC-first workflow 一节。 参照范本：[RFC-20261109-001（GLM-5.3 MTP5）](http://10.246.63.42:9009/?page=rfc)。

______________________________________________________________________

## 1. 目的与角色

- RFC 是**规范性规格与唯一事实源**：实现 agent 在不参考任何现有实现代码的前提下， 仅凭 RFC 应能完整复现该系统。
- 角色：**作者**（人或 agent，负责规格完备性）、**评审者**（按检查清单 §7 把关）、 **实现 agent**（按附录 B 分解开发、按 Gate 验收）、**讨论面**（RFC 平台在线评论）。

## 2. 核心原则（六条，违反任何一条视为不合格 RFC）

| #   | 原则                | 含义                                                                                                                                  |
| --- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Spec-first**      | 新特性先在 RFC 落为编号需求，实现跟随规格；禁止从代码反推 RFC（正向设计：动机→原理→对比→端到端→规格→验收）                            |
| 2   | **Spec, not code**  | 不含实现代码，至多伪代码；语义必须精确（索引对齐、归一化次数、错误语义逐条写死）                                                      |
| 3   | **双受众**          | 人读得懂（附录 A 知识依赖 + 阅读路径）；agent 能执行（需求可编号、可分解、可测试，附录 B）                                            |
| 4   | **验收契约化**      | 每条需求绑定测试矩阵条目；**无对应测试的需求视为未实现**                                                                              |
| 5   | **Keep it current** | 实现偏离、新决策、已解决的开放项 MUST 在同一变更内回写 RFC                                                                            |
| 6   | **证据与事实分离**  | 实测数字标注来源（文档/现场报告）；环境相关数字（基线、阈值）MUST 标注"新环境需重测"，MUST NOT 写死为规格；未验证假设 MUST 标注为假设 |

## 3. 编号体系（强约定，全文可逐条引用）

| 前缀           | 含义                                                                                                                               | 示例         |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| `REQ-<域>-<n>` | 规范性需求，域代码：ARCH（模型结构）/ DATA（数据）/ FWD（前向）/ LOSS（损失）/ RT（运行时）/ EXP（导出）/ SRV（服务）/ CLI（接口） | `REQ-ARCH-1` |
| `ADR-<n>`      | 设计决策记录：决策 / 备选 / 权衡 / 状态                                                                                            | `ADR-5`      |
| `G-A<n>`       | 验收 Gate：指标 + 阈值 + 测量方式                                                                                                  | `G-A1`       |
| `T-<类>-<n>`   | 测试矩阵，类：UNIT / PAR / SMOKE / EVAL                                                                                            | `T-UNIT-3`   |
| `M<n>`         | 里程碑，含 go/no-go 出口条件                                                                                                       | `M3`         |
| `F<组>.<序>`   | 特性分解条目（附录 B）                                                                                                             | `F3.1`       |
| `A<n>`         | 知识依赖条目（附录 A）                                                                                                             | `A2`         |
| `DFX-<n>`      | （反向整理时）遗留缺陷的目标语义修正                                                                                               | `DFX-2`      |
| `E-<n>`        | （现场修复后）提炼的工程经验规则                                                                                                   | `E-5`        |
| `OPEN-<n>`     | 开放问题，每项 MUST 带决策标准                                                                                                     | `OPEN-1`     |

## 4. 语言与写作规则

1. **需求语义**：MUST / SHOULD / MAY 按 RFC 2119 解释；否定形式 MUST NOT / SHOULD NOT。
2. **伪代码风格**：块伪代码 + 关键算法 MUST 给一个**工作示例**（小规模逐步演算）， 让读者可手工验证索引/对齐语义。
3. **表格优先**：枚举、映射、对比一律表格；规格性表格不得有"待定"单元格。
4. **错误语义表**：凡有边界条件的模块，MUST 用"条件 → 行为（raise 的报错文案 / 降级契约）"表格穷举。
5. **接口契约表**：数据结构、环境变量、CLI 参数、键映射 MUST 用表（字段/形状/类型/默认/语义）。
6. **可追溯性**：每条规格决策能回答"为什么"——追溯到原理节或 ADR；纯经验规则进 E-\*。

## 5. 文档结构（正文 12 节 + 双附录）

| 节         | 名称                      | 要求                                                                                                                              |
| ---------- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| §0         | 术语与约定                | 符号约定表；编号体系说明；附录导航                                                                                                |
| §1         | 动机                      | 问题是什么；量化痛点（实测数字）；为什么必须现在做                                                                                |
| §2         | 原理                      | 机制解释到"为什么有效"；关键性质编号化（作为全部设计的根源）；SHOULD：后续规格逐条可回溯                                          |
| §3         | 与既有方案的区别          | ≥1 条替代路线对比表（架构/接口/目标/边界）；选型理由；明确"这不是什么"                                                            |
| §4         | 端到端方案                | ASCII 架构图；数据/控制流；模式取舍表；闭环（含数据转化、运行模式）                                                               |
| §5         | 目标与非目标              | 非目标 MUST 明确排除项（防止范围蔓延）                                                                                            |
| §6         | 指标与验收 Gate           | `G-A*` 表格：指标/规范要求/测量方式；环境相关阈值标注"需重测"                                                                     |
| §7         | 设计决策记录              | `ADR-*` 表：决策/备选/权衡/状态；含"MUST NOT 重新开挖"条款                                                                        |
| §8–N       | 规范性规格（分域）        | `REQ-*` 按域编号；错误语义表；契约表；每条 MUST 可独立验收                                                                        |
| §N+1       | 评测与验证方案            | 程序可复现（到命令级）；基线数据表（标来源）                                                                                      |
| §N+2       | （条件）遗留缺陷修正 DFX  | 仅反向整理时：目标语义 vs 历史行为，重实现用修正后行为                                                                            |
| §N+3       | （条件）工程经验规则 E-\* | 教训 → 规范规则，标来源；声明进入评审清单                                                                                         |
| §N+4       | 开放问题                  | 每项带决策标准与计划                                                                                                              |
| §N+5       | 测试矩阵                  | 分层 T-UNIT/PAR/SMOKE/EVAL；与 REQ 双向映射；"无测试=未实现"声明                                                                  |
| §N+6       | 里程碑                    | M0..Mn；go/no-go 出口条件                                                                                                         |
| §N+7       | 横切约束                  | 质量工具链、版本面、合规/可复现、文档同步                                                                                         |
| §N+8       | 相关工作                  | 论文/报告/内部文档，标注各自回答什么问题                                                                                          |
| **附录 A** | 知识依赖地图（人读）      | A.1 依赖清单（解释/用在哪/深度分级 ★★★★~★/材料）；A.2 按角色阅读路径（含时长）；A.3 内部文档伴侣表（声明非规范性）                |
| **附录 B** | 特性分解（agent）         | B.0 固定工作流；B.1 特性树（Feature→REQ→T→出口）；B.2 依赖图（关键路径/可并行面）；B.3 增量 DoD；B.4 前置确认事项；B.5 风险与回退 |

## 6. 双受众硬性要求

- **人能读懂**：附录 A MUST 存在；术语首次出现即可在 A.1 找到出处；评审者有 ≤1h 快速路径。
- **agent 能执行**：附录 B MUST 存在；B.1 特性粒度 = 一个可独立提交的开发增量； B.4 MUST 列出 agent 需向人确认的前置事项（硬件、数据产能、基线重测、版本锁定）。

## 7. 质量检查清单（作者自检 = 评审检查）

- [ ] 每条 MUST/SHOULD 均有编号，可被独立引用
- [ ] 无实现代码；伪代码 + 工作示例齐备
- [ ] 错误语义表穷举边界条件（含降级路径）
- [ ] 每条规格可追溯到原理节或 ADR（无"凭空出现"的规格）
- [ ] 替代方案 ≥1 条且有权衡记录（ADR）
- [ ] 环境相关数字标注"新环境需重测"；假设标注为假设
- [ ] 每条 REQ 绑定 T-\* 测试；每条 Gate 有测量方式
- [ ] 附录 A/B 齐备；B.1 粒度可开工；B.2 有关键路径
- [ ] 开放问题全部带决策标准
- [ ] 状态行（vN 草案/评审中/已接受）与日期齐备

## 8. 生命周期与提交

**状态机**：`草案 → 评审中 → 已接受 → 实现中 → 已交付`（头部状态行维护；实现偏离回写时版本号 +1）。

\*\*提交（RFC 平台 http://10.246.63.42:9009）**：

```bash
# 1) 登录拿 token
curl -s -X POST http://10.246.63.42:9009/api/login -H "Content-Type: application/json" \
  -d '{"employee_id":"<工号>","password":"<密码>"}'

# 2) 创建 RFC（正文 markdown；返回 {"id":N,"code":"RFC-YYYYMMDD-001"}）
curl -s -X POST http://10.246.63.42:9009/api/rfcs -H "Content-Type: application/json" \
  -H "X-Auth-Token: <TOKEN>" -d @payload.json   # {"title":..., "content":<全文>}

# 3) 逐个挂载文档（伴侣文档/现场报告）
curl -s -X POST http://10.246.63.42:9009/api/rfcs/<RFC_ID>/files \
  -H "Content-Type: application/json" -H "X-Auth-Token: <TOKEN>" \
  -d @doc_payload.json   # {"filename":..., "content":<全文>}

# 4) 更新已有文档：PUT /api/rfcs/<RFC_ID>/files/<FILE_ID>
# 验证：GET /api/rfcs（带 token）
```

**双源约定**：仓库为事实源（`docs/` 下版本化），平台为讨论面（在线评论/修改）； 重大修订两处 MUST 同步，以仓库 git 历史为审计依据。
